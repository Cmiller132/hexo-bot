What the model sees — the input entities

The Hexo board has no limits. Because of this, the model has no grid and no fixed input vector. The builder converts each position into a graph of typed entities: the stones, the live windows, 4 state latents, and the legal cells. Relations from frozen vocabularies connect the entities, and each vocabulary is folded under the 12 symmetries of the board. All data on this page comes from one real position of a real game against the served model.

01the four entity sets

The position below comes from ply 11 of the captured showcase game. Mantis Shrimp v2 (blue, player 0) will place the first stone of its turn. The builder makes these entities:

  • 11 stones — one node for each stone. The only node feature is ownership relative to the side to move (own or opponent). The coordinates of a stone do not enter its features. Geometry enters only through the typed relations below.
  • 154 live windows — a window is a segment of six cells along one axis. A window is live when it contains one stone or more, of one player or of both players. Each possible win is one window.
  • 4 state latents — position-level rows without a board location. Each latent initializes from a learned base plus an embedding of moves_remaining (1 or 2 stones left in the turn). moves_remaining is the only whole-position scalar in the input. The latents carry global context through the trunk.
  • 420 legal cells — each empty cell in a distance of 8 or less from a stone, in the canonical order of the engine. 152 cells are covered. The other 268 cells are not in a live window and start from generic feature embeddings.

02window patterns — a vocabulary of 377

The state of a window is its six slots. Each slot is empty, own, or opponent, relative to the side to move. This gives a ternary string. The same physical window, read from the other end, gives the string in reverse. Because of this, the patterns are folded under reversal. The 728 ternary strings that are not empty make 351 mirror pairs and 26 palindromes: 377 canonical patterns.

Each live window enters the network as the learned embedding of its pattern. The status of a window (own only, opponent only, contested) is a function of the pattern, and a separate status feature does not exist.

03typed relations

All geometry enters through relation types. Each vocabulary is folded under the 12 symmetries of the board. As a result, a position and its rotation, reflection, or colour swap give identical inputs.

  • Stone ↔ window: 1,458 occupancy classes. A message between a stone and a window that contains it has a type. The type is the joint of the full window pattern and the slot of the stone. The fold applies to the pattern and the slot together. A stone is in a maximum of 18 windows (six on each axis).
  • Cell ↔ window: 726 decoder classes. The same joint typing, for the empty slots of a window: the pattern plus the position of the vacancy. These classes type the cell reads in the trunk and the incidence terms in the heads.
  • Stone → cell: 192 radius classes. Each legal cell reads the stones in a hex radius of 8. The type of each edge is the product of three invariant classes: the orbit-48 class of the offset vector (fig 3), own or opponent, and shared axis or not. 48 × 2 × 2 = 192.
  • Action rows: 729 post-placement classes. Each legal move is also encoded by its results: the 18 windows that the new stone would occupy. The type of each window is its post-placement pattern, joint with the placement slot (fig 5).
The joint tables are one enumeration. The 729 patterns × 6 slots give 2,187 reversal orbits. No live window uses the three orbits of the empty pattern. The 2,184 orbits that remain divide into the 726 decoder classes (empty slots) and the 1,458 occupancy classes (occupied slots). The builder asserts these identities at import time.

04what the input does not contain

The input does not contain absolute coordinates, axis identity, move history, the ply number, or manual tactical scalars. All model knowledge enters through the entities and the typed relations above.

Each input value is invariant under the 12 symmetries of the board. As a result, the network cannot know the difference between a position and its rotation, reflection, or colour swap. The outputs for all of them are identical. Only the order of the legal list can change. A replay test transforms full game histories through the engine and compares the permuted outputs.

Equivariant architectures tie the weights: inputs that turn give outputs that turn. Here the inputs are invariant: inputs that turn are the same inputs. The two methods use zero augmentation.
